本轮改动：

- MiniMax、Kimi 使用递归文件事件定位变化，静止历史不再逐个探测。事件丢失、根目录重建、监听失败会触发全量恢复；周期性全量核对作为兜底。时间过期仍在每次检测中计算。旧 MiniMax 任务原地恢复写入可在下一次检测中识别。
- Codex 以原始字段的短期摘要识别未变化记录，复用已脱敏元数据；继续每两秒读取日志增量，不保存未脱敏的原始标题或输出。
- 菜单栏移除空的外观跟踪子视图，使用外观观察；不对无变化状态重复配置视图、写布局属性；关闭的左键菜单不强制计算 SwiftUI 布局，打开前立即更新。
- 连续节奏缓存按图形方向、警戒边框及 1/8192 填充步长判定，避免不可见浮点漂移。语义阈值仍即时生效。每帧生成时清理临时绘图对象。
- 显示器发现改为配置/唤醒事件驱动，并定期核对；缺少目标时仍逐秒重试，原有亮度维护周期保持。

## 原生动画专项复核

本次没有改动或重新安装正式渲染后端；独立试验没有找到兼顾稳定收益和现有体验的合格替代方案。安装版本仍为上述 SHA-256，签名复核通过。不能把复测称为“新优化版安装后”的结果。

同一个 65×22 点、三个环形图的独立原生菜单栏实验，以相同 12 fps 播放：复用一张 NSImage 并替换位图表示约 2.32% CPU，常规更换 NSImage 约 2.33%；差异不足以说明收益。这是八秒短窗、预热后测试，不是完整应用结果，也不是精确的性能下限。先前预着色缓存、图像格式、cell 赋值及图层开关的试验也没有稳定的大幅收益。

独立静态图标约 0.051% CPU；交给 CAKeyframeAnimation 播放约 0.057%。这说明合成器路径有潜力，但低进程 CPU 本身不能证明体验等价，也未计入 WindowServer/GPU 成本。

实机采样出现 `NSStatusItem._redrawReplicantSnapshot → NSView._renderLayerInContext → CALayer.renderInContext`。Apple 文档明确说明 `CALayer.render(in:)` 忽略 render tree 中的动画。因此仅用 CAKeyframeAnimation 不能据此认为所有菜单栏副本都会持续播放；存在副本停帧风险。这是调用栈与文档形成的技术判断，尚未完成多屏视觉验证，未将试验后端安装为正式版本。

参考：[Apple CALayer.render(in:)](https://developer.apple.com/documentation/quartzcore/calayer/render%28in%3A%29)。

目标与代价：

- 没有活动任务、没有离线脉冲或自测时，现有代码只生成静态一帧，不启动持续播放循环；完整应用在真正空闲时是否低于 1%，本次仍未验证。检测周期和配额刷新继续保留。正在执行本次 Codex 任务时不能称为完全空闲。
- 保留现有持续可见动画、原生自动着色及多屏行为，目前没有证据能保证 1% 以下；这不是断言所有实现均不可能。
- 降帧或改成开始/结束时短暂动画会改变持续运动效果，虽然可以保持任务检测和数据刷新及时性，但不符合本轮要求，未采用。
- 预着色的像素缓存增加内存、缓存失效和多外观验证成本，当前收益不足；GPU/独立浮窗方案还需处理副本、Spaces、全屏、缩放、亮暗和点击高亮行为，不能视为直接可替换方案。

试验只存在于临时目录 `/tmp/aiquotabar-perf-round3` 及上一轮诊断目录；没有禁用任务检测、防休眠、网络刷新或正式应用的动画，也没有把合成器试验的低 CPU 数字当作完整应用性能。
