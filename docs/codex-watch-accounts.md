# 关注账号（团队云端跨设备）

## 这是什么

让一台 Mac 把自己的 Codex 额度**显示在另一台 Mac 的菜单栏里**，而不必在那台 Mac 上登录这个账号。

典型场景：小王有一台常驻跑 Codex 的机器，那台机器登录了某个账号；他自己另一台 Mac 想盯着这个账号的额度用，但不想、也不需要在那台 Mac 上登录它。

关注方要填的**只有一个邮箱**。不需要地址、端口、访问密钥，也不需要在关注方登录 Codex。

## 传输：复用已有的团队云端通道

额度本来就产生在云端（OpenAI 的服务器），而这个 app 早就有一条把额度同步到云端、再让别的设备读回来的通道：
团队云同步（`/v1/quota-samples`，按设备凭据鉴权）。关注功能直接复用它，**没有新开端口，也没有第二套凭据**。

```
登录了账号的那台 Mac                         关注方那台 Mac
┌────────────────────────────┐             ┌──────────────────────────────┐
│ 本机 Codex 凭据 → 抓额度    │             │ 「我关注的账号」填一个邮箱    │
│            ↓               │             │            ↓                 │
│ 上报前过滤：                 │  POST       │ GET /v1/quota-samples         │
│  只放行勾选的 Codex 账号     │ ──────────► │  按账号名取回最新快照          │
│            ↓               │  设备凭据    │            ↓                 │
│ /v1/quota-samples          │             │ 与本机账号合并后按账号分组显示  │
└────────────────────────────┘             └──────────────────────────────┘
                    同一个团队 = 同一份数据，谁上报的都互相可见
```

## 为什么不是另外两条路

| 方案 | 为什么不选 |
| --- | --- |
| 把 `auth.json` 拷到本机 | 两台机器共用同一个 `refresh_token`，轮换时会互相把对方挤下线（`refresh_token_reused`）。 |
| 自己搭一条点对点通道 | 要用户手填地址、端口和访问密钥，只在同一 Wi-Fi 下能用。v1.32.x 试过，见下节。 |
| 关注方自己登录这个 Codex 账号 | 需求本身就是要「不登录也能看」，而且多一份登录就多一份 `refresh_token` 轮换风险。 |

**Codex 登录凭据永远不离开登录它的那台机器**。线上传输的只有额度百分比、重置时刻、套餐名——没有任何能拿去调用 OpenAI 的东西。

## 设置在哪

**设置 → 服务商 → Codex → 关注账号**，一个区块里两半：

- **允许其他 Mac 关注我的账号**（分享侧）：全局开关 + 逐账号勾选。
- **我关注的账号**（关注侧）：一个邮箱输入框 + 一个添加按钮。

两半互不依赖。

## 使用步骤

1. **两台 Mac 都在「设置 → 团队」里**，创建或用邀请码加入**同一个团队**。
   - 只需要做一次。成员口令存在本机钥匙串，之后不用再填。
   - 团队是这条通道的鉴权基础：云端按团队隔离数据，没有它就什么都读不到。
2. **分享方那台 Mac**：打开「允许其他 Mac 关注我的账号」，勾选要分享的账号，
   并确保「团队」区块里的**共享账号额度**是开着的（额度要有地方可同步）。
3. **关注方那台 Mac**：在「我关注的账号」里填入那个邮箱，点「添加」。
4. 之后跟着正常用量刷新更新，菜单里出现该账号的分组行，状态行显示「团队云端 · N 条 · 更新于 …」。

## 状态为什么分三种

三种「看不到数据」对应三种完全不同的用户动作，混成一句「无数据」会让人以为该重装点什么：

| 状态 | 含义 | 用户该做什么 |
| --- | --- | --- |
| `noTeam` | 本机没加入团队，没有云端通道 | 去「设置 → 团队」加入 |
| `waitingForPublisher` | 通道正常，但云端还没有这个邮箱的快照 | 让对方勾选这个邮箱，并确认那台 Mac 在运行 |
| `available` | 有数据 | 不用管 |

## 安全边界

1. **默认拒绝。** 打开分享开关后，只有**逐个勾选**的 Codex 账号会被上报；没勾的一个都不传。
   账号名为空的未归属额度同样不上报（它没法被按邮箱关注，留着只会让人以为在共享）。
2. **开关关闭 = 行为完全不变。** 没打开「允许其他 Mac 关注我的账号」时不做任何过滤，
   所有 Codex 额度照旧按「共享账号额度」的原有行为上报。老用户升级后行为不变。
3. **只管 Codex。** 这个开关不影响 Kimi / GLM / MiniMax 原有的团队共享行为。
4. **不转发别人的账号。** 分享名单取自**本机登录着的账号仓库**，不是从
   `providerUsageSections` 里取的——后者已经和云端合并过了，里面混着别人上报的账号。
   从那里取会让本机把同事的额度当自己的再转发一次。
5. **凭据不出机器。** 线上只有额度百分比、重置时刻、套餐名。没有 token、没有 API key。
6. **鉴权沿用设备凭据。** 没有新增的公开端点，也没有 app 级共享密钥；
   团队隔离（`docs/team-isolation.md`）的既有约束一条都没有放松。
7. **可以随时收紧。** 取消勾选后，该账号在下一次用量刷新时就不再上报。
   这个窗口最多一个刷新周期。

## 与 v1.32.x 的差别

v1.32.1（build 62）里这个功能是**局域网点对点**：owner 端自己起一个明文 HTTP 服务，
对端手填 IP、端口和一份自建的访问密钥去读。这条路要求两台 Mac 在同一个 Wi-Fi 下，
而且用户要去「手机看板」里翻密钥——和「只填个邮箱」的预期差得很远，所以整个删掉了。

删除的内容：局域网 HTTP 端点 `/api/v1/watch/quota`、`CodexWatchPeerClient` /
`CodexWatchPeerStore` / `CodexWatchResponseBox` / `CodexWatchPeerModel` /
`CodexWatchProjector` / `CodexWatchPayload` / `CodexWatchGrantStore`，
以及手机看板服务为此多起来的那条「被关注也要监听」的分支。
手机看板回到「只有自己打开才监听」的原有语义。

UserDefaults 里的 `codexWatch.isServing` / `codexWatch.grants.v1` 会被读取并迁移，
用户之前勾过的账号不用重新勾。

## 已知边界

- **只覆盖 Codex。** 其它 provider（Kimi / GLM / MiniMax）各有各的凭据模型，
  混进来会让「允许分享」语义变模糊。
- **需要分享方那台 Mac 在运行。** 它关机或退出，云端里的快照就会停在最后一次上报的时刻，
  状态行会显示那是什么时候；重新打开后自动恢复。
- **两台 Mac 必须在同一个团队里。** 这是鉴权边界，不是可用性折衷。
