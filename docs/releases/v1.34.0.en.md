# v1.34.0 — Watching an account by email: no team, no key

macOS build 64.

## Watching an account: knowing the address is enough

The last two releases both made "see the quota if you know the account" harder than it needs to be. v1.32.1 was a LAN peer-to-peer link requiring a typed IP, port and a hand-rolled key; v1.33.0 moved onto team cloud sync, which fixed the transport but still required both Macs to join the same team with an invite code.

This release removes that middle layer too: **anyone running AI Quota Bar who knows an email address can read that account's quota.**

- No team, no invite code, no access key, no IP or port
- **The two Macs do not need to be on the same network** — the transport goes through the app's own cloud service
- The watching Mac does **not** need to sign in to Codex
- The sharing Mac only has to turn on "Let other Macs watch my accounts" and tick the address

Still under Settings → Providers → Codex → 关注账号.

### Data flow

```
the Mac holding the sign-in                  the Mac that watches
┌────────────────────────────┐             ┌──────────────────────────────┐
│ local Codex credentials    │             │ enter one email under         │
│        ↓                   │             │ "Accounts I watch"            │
│ fetch quota                │  POST       │        ↓                     │
│ project only ticked accts  │ ──────────► │ GET /v1/watch/quota?email=…   │
│ percent / reset / plan     │  app's key  │ the address is the lookup key │
│        ↓                   │             │        ↓                     │
│ /v1/watch/publish          │             │ grouped by account in the menu│
│ replace-all: [] = unshare  │             └──────────────────────────────┘
└────────────────────────────┘
```

Codex credentials **never leave the machine they are signed in on**. Only remaining percentages, reset times and the plan name travel.

## The boundary of this channel, stated up front

**The read path is open to anyone who knows that email address.** This is a direct consequence of "no team, no key", not an oversight: without either, the server has no secret it can check. The real authorization is the owner ticking that address one by one — ticking it means "a Mac that knows this address may see my quota", and unticking deletes it from the cloud immediately.

The server stores `sha256` of the normalized address, so the table never holds a plaintext email. But be precise about what that buys: **the hash is hygiene, not access control** — anyone can compute the lookup key for an address they know.

Within that, the following still hold:

1. **Default deny.** With the switch on, only individually ticked Codex accounts are published; unticked ones are not sent at all. Quota with no account name is not published either — it cannot be watched by email.
2. **Only percentages cross the wire.** Remaining percentage, reset time and plan name. No token, no API key, and **no absolute usage** — absolute counts would expose how much this person actually burns.
3. **Revocation is immediate.** Publishing is replace-all, so unticking deletes the row right away: no waiting for the next refresh, and no separate revoke endpoint that could half-apply.
4. **Stale data does not pose as current.** A snapshot older than 3 hours is labelled "these numbers may be old" rather than rendered as a live value. The row is kept — an account you explicitly asked to watch should not vanish.
5. **Reads are visible.** The sharing side shows how many times each account has been read and when it was last read. Count and time only, **no viewer identity**; the owner's lever is "untick", not "blocklist this reader".
6. **No relaying someone else's account.** The share list comes from the accounts signed in on this Mac, not from the menu's cloud-merged view — the latter contains teammates' reported accounts, and sourcing from it would make this Mac republish a colleague's quota as its own.
7. **The team system is untouched.** `/v1/watch/*` is its own namespace and cannot read team data, device credentials or the admin console. No team-isolation guarantee was relaxed.
8. **Rate limited.** Reads are limited per source IP (120/hour), publishes per publisher (120/hour).
9. **One publisher per address.** A second publisher is refused (409); otherwise the original publisher's later "unshare" could not delete the row and the account would stay published forever.

Endpoint authorization uses the app's built-in key (called `SYNC_TOKEN` server-side), which every install already carries — zero configuration. **It is not a secret**: it sits in the binary. What it does is keep casual `curl` out, give reads an attribution bucket and give rate limiting something to key on. The real authorization is the per-account tick in point 1.

## Turning the switch on now fetches by itself

What gets published comes from the quota this Mac just fetched. Right after the switch is turned on there is usually no data yet, so the switch now runs a usage refresh first and publishes what it gets — no manual refresh needed.

The misleading empty state is gone too. When the list is empty the app no longer says "No Codex account is signed in on this Mac" (it may simply not have fetched yet, which calls for the opposite action), and instead says the quota has not been fetched, with a retry button.

## Three problems fixed

- **A failed fetch deleted the cloud snapshot.** On a cycle where the Codex fetch produced nothing, the app published an empty set — and since publishing is replace-all, one network blip silently unshared the account. It now publishes nothing when there is no local data.
- **Expired numbers were shown as current.** The status check tested "is there a snapshot" before "is it stale", and the cached snapshot is deliberately kept on a stale response (the row must not disappear), so numbers 2.5 hours old rendered as "Cloud · N entries". Staleness is now checked first.
- **The shareable account list was stale.** It was `@State`, refreshed only when the panel opened and when accounts were added or removed — a quota refresh did not update it. It is now a computed property that always follows the latest fetch.

## Differences from the previous two releases

**v1.32.1 (build 62)**: LAN peer-to-peer. The owner machine ran its own plain-HTTP server; the watcher typed an IP, a port and a hand-rolled key; same Wi-Fi only. Removed: the LAN endpoint, seven `CodexWatch*` types, and the "keep listening so an account can be watched" branch the mobile dashboard grew.

**v1.33.0 (build 63)**: moved onto team cloud sync. This release **reverts** that version's changes to the team channel — upload filtering and the startup read condition are undone, and team sync behaves exactly as it did before any of this work.

Upgrading from v1.32.1: previously ticked accounts migrate automatically (read from `codexWatch.isServing` / `codexWatch.grants.v1`) and do not need re-ticking.
