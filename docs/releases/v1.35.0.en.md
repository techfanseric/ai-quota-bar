# v1.35.0 — a placeholder with a choice, a trend in the ring, honest timestamps

macOS build 68. This release also changes how the app is installed.

## Installing is now one double-click

The DMG asked for three steps: download, mount, drag. The installer package asks for one, and it does two things a drag-and-drop cannot:

- **The running app is closed before its bundle is replaced, and comes back afterwards.** A menu bar app that silently stops being a menu bar app until you happen to notice is a worse outcome than one extra click
- The installer deletes itself when it is done, so it does not sit in your Downloads folder

Both installer scripts run as root and were verified twice on a real machine before this shipped.

**One thing worth knowing**: the package is **not Developer ID signed and not notarized** (the app inside it is ad-hoc runtime signed). Double-clicking it after a browser download makes macOS warn more than it did for the DMG. If it says the developer cannot be verified, Control-click the package and choose Open, or use Privacy & Security → "Open Anyway". After that it behaves normally.

The release still carries a DMG for anyone who prefers it. The two are functionally identical.

## The menu bar placeholder is a choice now

The old setting was a single toggle — "show the provider count when everything is hidden". That is a boolean expressing two shapes, so it had no room for a third. It is now a picker:

| Option | What the menu bar shows |
|---|---|
| **OpenAI connectivity** (default) | A muted ring with a reachability mark in the centre (check, cross, or probing) |
| Provider count | A muted ring with the number of enabled providers |
| Brand mark | The app icon's letterform |

Connectivity is the default because a placeholder has no quota to show, and "can I launch ChatGPT right now" is the one thing still true at that moment that you actually care about. Without it, the placeholder is a decorative dead ring.

The mark is deliberately unlike "Codex is down": that state stacks a red ring, a red pill and a pulse. This keeps the ring muted and completely static, and carries state only in the centre mark, so it stays readable at twenty-odd pixels. Reachable uses the neutral label colour rather than green — this app's semantic colours are amber and red, and green would be a third thing to learn.

The tooltip gains a line explaining the mark, because a glyph that small has no other explanation.

## An account with only a weekly window finally gets a shape

An account with a Weekly window and no 5h window had a single pace number spanning days, which says nothing about shape. Now:

- The ring and the inner channel both resolve to Weekly for such accounts. You may have set the ring to 5h, but there is no 5h to show — Weekly is the quota you were actually asking about
- The inner channel draws the window's own history as a **curve** instead of the bidirectional pace sector
- The curve needs at least **two samples** to exist (one point draws no line, and would leave a lone dot where the sector should be, which reads as a rendering bug) and is capped at **24 points** (the menu bar is ~22px wide; more is just aliasing)
- The horizontal axis is each sample's position on **the window's own timeline**, not its index in the array. Ordering by index makes two samples look like a full week's swing, which is a lie

The inner channel is its own setting. If you point it at a different window, the sector keeps that channel — a 10% weekly overspend is the signal most worth seeing, and the trend should not take it away.

## Watched accounts were showing the wrong time

The account row's trailing time is the last sample time. It read `Watch · 10/11 23:59` for a snapshot taken five minutes earlier.

The cause was two hops: `CodexUsageDataMapper` dropped the real fetch time (`sampledAt: nil`), and the publish projection then fell back to `endTime` — which for Codex is `resetsAt`, the end of the window, days ahead. **The data was current and the time was wrong, which reads worse than having no time at all**: you would conclude something was broken.

Fixed at four layers:

- **Source** — every Codex row carries the real fetch time
- **Publish** — never falls back to a window boundary
- **Read** — a sample time later than "now" is not a time, it is a bug report, so it falls back to the publish time
- **Server** — future sample times are clamped at publish

The last two exist so that an owner who never updates still produces correct rows for everyone else. Verified in production: the other Mac is still on the old build and keeps sending the future timestamp, the server rewrites it on arrival, and every reader gets the right time. `resetsAt` is a separate field and is untouched — the "35% over · 10/11 23:59" reset line still shows correctly.

## Smaller corrections

- A long account name **truncates instead of shrinking**. A shrunken name makes the rows in the same block inconsistent, which from a distance reads as "this one account is special"
- When width runs out, the **plan name yields before the account name does** — the plan is decoration, the account is identity
- Timestamps are atomic and are never cut into a half `10/5 11:1`
- Cross-day timestamps carry the date (`9/28 11:50`), in the admin console as well as the menu. A bare `11:50` does not say which day's snapshot it was
