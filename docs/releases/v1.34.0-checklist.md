# v1.34.0 release record

- User rejected v1.33.0 too, but for a different reason than v1.32.1: "我希望不加入团队也能实现这个共享，只要知道账号就行了啊". Two rejections, two different layers of ceremony removed — first the access key and LAN address, then the team and invite code. What the user actually wanted both times was a single email field.
- Version 1.34.0, macOS build 64. Minor bump: new server endpoints and D1 tables, plus a revert of v1.33.0's team-channel changes.
- Commits: `7edfac6` (watch by email alone — backend, migration, app, three defect fixes), `b1a9d23` (release notes + version bump + homepage version strings), `0d0a234` (changelog feed sync).
- **Backend shipped ahead of the app.** `migrations/0009_codex_watch_share.sql` applied to the remote D1 and the Worker deployed before the app build, so the feature was testable from the installed app as soon as it landed. Verified in production with real requests: 401 without a token, 401 with a wrong token, publish 200, normalized-address read-back 200, unpublished address 404, out-of-range percentage 400, read counting, and revoke-by-empty-publish. Probe rows were deleted afterwards.
- Authorization is the app's built-in `SYNC_TOKEN`. Verified it is the same value as the hardcoded `CloudSyncSettings.defaultServiceToken` by probing a SYNC_TOKEN-gated route with a deliberately invalid payload: real token → 400 `invalid_payload` (auth passed, no DB write), bogus token → 401. Documented as a speed bump, explicitly **not** as authentication.
- **The read path is open to anyone who knows the address.** This is the direct cost of "no team, no key". Stated plainly in the release notes, the settings copy and docs/codex-watch-accounts.md rather than implied to be protected. sha256 of the normalized address is stored server-side so no plaintext email lands in the table, and the docs say explicitly that this is hygiene, not access control.
- Defensive properties kept anyway: default deny per account, percentages only (never absolute usage — that would expose burn rate), replace-all publishing so unticking revokes immediately and cannot half-apply, 3-hour staleness that labels rather than hides, read counts visible to the owner with no viewer identity, rate limits on both paths, and 409 when a second publisher tries to claim an address (otherwise the first publisher's later un-share could not delete the row).
- v1.33.0's team-channel changes were **reverted**, not kept: the upload filter, the startup read condition and the team-only refresh guard are all back to their pre-feature state. Team sync is untouched by this release.
- Three defects found and fixed, all of them mine:
  - **A failed fetch unshared the account.** A cycle with no local Codex quota published an empty set, and since publishing is replace-all, one network blip deleted the published snapshot. Now publishes nothing when there is no local data.
  - **Stale numbers rendered as current.** `status(for:)` tested snapshot presence before staleness, and the cached snapshot is deliberately kept on a stale response so the row does not vanish — so numbers 2.5 hours old displayed as "Cloud · N entries · updated …". Staleness is now checked first.
  - **Turning the switch on fetched nothing.** `CodexWatchStore.onChange` had been changed from a full usage refresh to a watch-only refresh, which removed the only thing that populated `providerUsageData[.codex]`. The shareable-account list stayed empty and the UI claimed "No Codex account is signed in on this Mac" — to a user who was signed in. `refreshCodexWatch()` now refreshes usage first when sharing is on and there is no local data, behind a re-entrancy guard (since `refresh()` itself calls it at the end). The empty state was reworded to "quota has not been fetched" plus a retry button, and the list became a computed property because as `@State` it never updated after a quota refresh. The user reported this one as "我点了刷新才行的".
- Two of my own diagnoses during this session were wrong and had to be walked back: `~/.codexbar/config.json` is the codexbar CLI config (providers list), not the account store — the store is `~/Library/Application Support/CodexBar/managed-codex-accounts.json`; and reading the `email` claim out of `~/.codex/auth.json` does not tell you which account the app fetches quota for (the two disagreed, and the app's own sample store showed a third). The real cause of the empty list was the missing fetch, not the identity source. Lesson: when a list is empty, check whether there is data to list before theorising about which source it came from.

Cloudflare `npm run check` clean; `npm test` 118 tests, 117 pass / 1 fail — the pre-existing `tests/team.test.js:107` "dashboard session", verified on a clean tree in v1.32.1 and not touched here. - Deploy note (carried forward): the token must be selected by account name (`node.cyberic@gmail.com`), not by position in the token file — it is the last of six rows. **Handled wrong once this session**: a "masked" dump of that file used a regex that did not match backtick-wrapped tokens, so six Pages/Workers tokens were printed into the conversation. Rotating them was recommended to the user. Any future dump of that file must redact by line index, never by pattern-matching the token shape.
- Production Pages deployment verified: `/`, `/en/`, `/changelog`, `/en/changelog` all 200 showing v1.34.0; English changelog renders the English title; `/v1/app-update` reports 1.34.0 pointing at the v1.34.0 DMG; `/v1/watch/quota` answers 401 without a token, so the new namespace is live and gated.
- Known boundaries: Codex only; the sharing Mac must be running (a stopped publisher freezes the snapshot, and after 3 hours the state becomes "these numbers may be old"); one address can be published by only one Mac at a time; and the read path is open to anyone who knows the address, mitigated by per-account consent, immediate revocation, visible read counts and rate limits rather than by a shared secret.
